## 一分钟结论

SOSP 2026 于 9 月 9 日更新正式日程，62 篇录用论文被编入 12 个研究论文 session。与本站最相关的议程集中在多模型 serving、训练与推理仿真、RL 权重分发、确定性推理、GPU kernel 验证和 agentic kernel 优化。

## 精选论文

### 1. [Janus: Multi-LLM Serving at Production Scale](https://sigops.org/s/conferences/sosp/2026/accepted.html)

**54/100 · AI 基础设施 > 推理服务平台 > 网关、路由与弹性伸缩 · Model Serving at Scale**

Janus 用“服务级模型放置 + 引擎级显存管理”的双层设计承载生产多模型 serving：30 秒级稳态调度处理长期需求，0.5 秒级弹性环处理突发负载，xTensor 则把设备显存抽象为可伸缩资源。

**为什么值得关注：** 论文覆盖 768 张 Ascend 910C、62 个应用和每日 4560 万请求的生产轨迹；作者报告 SLO 达成率 0.97–1.0，并称每日可节省约 1.34 万 device-hours。它把多模型共置从局部 batching 问题提升为跨服务、跨时间尺度的容量编排问题。

**边界：** 结果来自特定 Ascend 910C 集群与生产工作负载；调度周期、节省比例和 xTensor 收益不能直接外推到 NVIDIA/AMD、不同模型组合或不同突发分布。开源仓库仍需复现实验核验。

[PDF](https://yangtonghome.github.io/uploads/Janus_SOSP2026.pdf) · [代码](https://github.com/Janus2026/Janus)

### 2. [M2K: Making the Model-Kernel Interface Explicit for Reliable CUDA Kernel Verification](https://sigops.org/s/conferences/sosp/2026/accepted.html)

**52/100 · 高效推理 > 运行时与内存 > Kernel 与算子优化 · GPU kernels and accelerators**

M2K 显式建模 ML framework 与 CUDA kernel 之间容易遗漏的接口语义：HFProbe 探测框架行为，cuKLEE 通过符号执行验证 kernel，目标是在性能优化后捕获静默错误。

**为什么值得关注：** 作者称在 Hugging Face、vLLM 和定制 kernel 上发现 181 个此前未知问题，仅 9 个误报；向 vLLM 报告的 26 个问题中已有 8 个修复、4 个确认。它为快速迭代的推理 kernel 增加了可审计的正确性关口。

**边界：** 符号执行受路径爆炸、建模完备性和支持算子范围限制；发现的“问题”数量不能等同于生产故障数量，已修复或确认的子集才是更强证据。误报和漏报仍需人工与真实硬件测试补足。

[PDF](https://arxiv.org/pdf/2603.24595) · [代码](https://github.com/system-pclub/M2K)

### 3. [LLM-42: Enabling Determinism in LLM Inference with Verified Speculation](https://sigops.org/s/conferences/sosp/2026/accepted.html)

**48/100 · 高效推理 > 服务与分布式推理 > 批处理与调度 · Predictable and Resilient AI Infrastructure**

LLM-42 通过 decode–verify–rollback 协议获得分布式推理的确定性：常态继续使用未经修改的高性能 kernel，在同步点验证结果，只有发现分歧时才回滚。

**为什么值得关注：** 它把“可复现”从禁用高性能 kernel 的静态约束改成运行时协议，适合调试、审计和跨副本一致性场景；公开实现基于 SGLang，可直接检查协议与系统集成方式。

**边界：** 确定性需要额外校验流量、状态管理与极端情况下的回滚；低开销结论依赖分歧稀少和特定运行配置。它保证执行结果可复现，不代表模型语义正确或服务天然容错。

[PDF](https://arxiv.org/pdf/2601.17768) · [代码](https://github.com/microsoft/llm-42)

### 4. [A Few GPUs, A Whole Lotta Scale: Faithful LLM Training Emulation with CrystalLLM](https://sigops.org/s/conferences/sosp/2026/accepted.html)

**47/100 · AI 基础设施 > 推理服务平台 > 可观测性与基准测试 · Predictable and Resilient AI Infrastructure**

官方议程将系统称为 CrystalLLM；对应预印本标题使用 PrismLLM。方法切分训练执行图，将少量真实 GPU 执行与解析模型结合，用小规模硬件重建大集群的迭代时间和显存行为。

**为什么值得关注：** 作者报告迭代时间误差 0.58%、峰值显存误差低于 0.01%，并以不足目标规模 1% 的物理 GPU 仿真最多 8192 GPU 配置；若可复现，可明显降低并行策略与集群规划的试错成本。

**边界：** 官方议程的 CrystalLLM 与预印本的 PrismLLM 存在命名差异，本页只因作者与论文内容对应而关联，不能视为官方别名确认。极端规模结果是仿真精度主张，不是实际 8192 GPU 训练吞吐证明。

[PDF](https://arxiv.org/pdf/2605.15617)

### 5. [Ave: Guiding Agentic GPU Optimization Using Data-Flow Invariants](https://sigops.org/s/conferences/sosp/2026/accepted.html)

**43/100 · 高效推理 > 运行时与内存 > Kernel 与算子优化 · GPU kernels and accelerators**

官方议程称系统为 Ave；对应预印本标题使用 ARGUS。方法让开发者用紧凑 DSL 声明数据流不变量，再以抽象解释与 SMT 在编译期筛掉语义错误的 agent 生成 kernel。

**为什么值得关注：** 作者在 MI300X 上报告核心 kernel 达到手写实现 99%–104% 吞吐，并在 200 个 KernelBench 任务上取得 100% L1、90% L2 正确率；它说明 agentic 优化若配合可验证约束，可能兼顾搜索速度与正确性。

**边界：** 官方 Ave 与预印本 ARGUS 的命名并不一致，本页只按作者和内容对应关联。评估集中在 MI300X 与选定核心 kernel，DSL 断言质量、SMT 覆盖面和迁移到 CUDA/NVIDIA 的效果仍需单独验证。

[PDF](https://arxiv.org/pdf/2604.18616)

### 6. [TensorHub: Scalable and Elastic Weight Transfer for LLM RL Training](https://sigops.org/s/conferences/sosp/2026/accepted.html)

**41/100 · AI 基础设施 > 集群与资源管理 > 网络与互联 · Predictable and Resilient AI Infrastructure**

TensorHub 把 RL 训练中的模型权重视为可引用对象，用 reference-oriented storage 避免反复复制，并按集群拓扑规划训练端到推理端的传输、版本一致性和故障恢复。

**为什么值得关注：** 作者报告独立权重传输相对 NCCL 最多减少 6.7× GPU stall、弹性权重更新相对 UCX 最多提升 4.8×，跨数据中心场景减少 19× stall；这正面命中大模型 RL 中被通信和版本切换吞噬的 GPU 时间。

**边界：** 峰值结果依赖具体网络拓扑、权重大小和并发模式；论文中的 1T 参数场景通过重复 260B 模型层构造，不能等同于真实 1T 模型训练。生产部署证据仍需结合公开 artifact 复核。

[PDF](https://arxiv.org/pdf/2604.09107)
